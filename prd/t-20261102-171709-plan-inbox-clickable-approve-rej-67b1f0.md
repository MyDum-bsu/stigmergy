# PRD — Plan inbox: clickable approve/reject для normal lane

ID: `t-20261102-171709-plan-inbox-clickable-approve-rej-67b1f0`
Source: raw request «Plan inbox: clickable approve/reject для normal lane без ручных команд».

## Goal

Человек утверждает план кликом в открытой странице плана, а не набором
`stg plan approve <ID>` в терминале. Клик несёт ровно тот же эффект, что и
команда: спека валидируется, коммитится в `dev` worktree, задача становится
runnable; отказ помечает план rejected и задачу — не runnable. Второй эффект:
действие из страницы попадает на доску как человеческое (`via=inbox`), чтобы
аудит не смешивал его с агентскими событиями.

## Non-goals

- Fast lane не меняется: `stg plan auto` уже проходит policy-approve без человека.
- Не вводим причину отказа (`reject --reason`) — отдельная задача, здесь отказ без текста.
- Не трогаем `stg plan preflight`, `stg plan render`, формат spec-файла и схему событий доски.
- Не открываем approve агентам: клик — это человеческое присутствие, а не новый программный путь.
- Не делаем удалённый/сетевой доступ: сервер только на loopback, никакой авторизации по аккаунтам.

## Use cases

1. Normal lane: `stg plan serve <ID> --open` → страница плана с двумя кнопками
   `Approve` и `Reject`. Клик `Approve` → страница результата «approved», задача runnable.
2. Normal lane, отказ: клик `Reject` → «rejected», задача не стартует, lead видит состояние.
3. High risk: то же самое, но approve проходит только если preflight уже зелёный
   (formal + mutant + critic + negative control); иначе страница отвечает 409 и объясняет, чего не хватает.
4. Уже решённый план: кнопок нет, вместо них строка состояния; повторный клик по
   сохранённой ссылке — 409, второго события на доске нет.
5. Fast lane / auto-approved: кнопок нет — решать нечего.

## UX

- Страница плана (`plan render`/`serve`) в конце документа получает блок действий:
  две кнопки, `Approve` — первичная, `Reject` — вторичная, обе `<form method="post">`.
  Ниактивного JS не требуется, работает и без него.
- После действия сервер отвечает короткой страницей: заголовок состояния
  (`approved` / `rejected`), ID задачи, ссылка «назад к плану» и — при ошибке —
  одна строка причины (`token expired`, `plan already decided`, `spec changed since render`).
- Ошибка не выглядит как успех: код ответа 400/403/409 и текстовая причина, без редиректа на страницу успеха.
- Ссылка с токеном одноразовая на действие и на текущий digest спеки: после approve
  тот же URL даёт 409, а не повторное событие.

## Edge cases

- Токен подделан/чужой/от другого плана → 403, состояние не меняется, `apply` не вызывается.
- Страница открыта до правки спеки, digest изменился → 409 `spec changed since render`, требуется перерендер.
- Двойной клик/две вкладки одновременно → одно событие доски, второй запрос 409.
- `plan_id` не найден в `.factory` → 404, без создания событий.
- High risk без зелёного preflight → 409 с перечнем недостающих артефактов, а не «тихий» approve.
- Сервер слушает только `127.0.0.1`; запрос с чужим `Host` отклоняется (CSRF/DNS-rebinding).
- Отказ (`reject`) для уже запущенной задачи запрещён: 409, доска не переписывается.
- TTY/браузер недоступен → `stg plan approve` остаётся рабочим путём (обратная совместимость).

## Risks

- Новый HTTP-обработчик, меняющий состояние гейта, — CSRF/replay поверх loopback.
  Снимается: одноразовый HMAC-токен от `plan_id+digest+secret`, проверка `Host`, POST-only.
- Кнопка approve на high risk обходит «человек посмотрел preflight» — снимается
  обязательной проверкой preflight-артефактов и явным текстом 409.
- Расхождение клика и CLI (разные проверки в двух путях) — снимается тем, что оба
  пути идут через одну функцию применения и один и тот же вызов валидации спеки.
- Токен в URL попадает в историю браузера/логи — принимается: токен одноразовый
  и привязан к digest; в логи токен не пишется.
- `plan serve` реализован на stdlib `http.server` без потокобезопасности —
  параллельные клики сериализуются блокировкой вокруг применения.
